## 4. Thiết kế dữ liệu

### 4.1 Dữ liệu hiện có và bổ sung dự kiến

| Entity | Giữ lại | Bổ sung/điều chỉnh đề xuất | Lý do |
| --- | --- | --- | --- |
| Job | title, departmentId, createdBy, description, requirements, location, salaryRange | DRAFT trong enum; benefits nullable; requirementsVersion int mặc định 1; version int | Nháp, quyền lợi, nhận biết JD đổi và chống ghi đè |
| Application | unique(jobId,candidateEmail), trạng thái ATS, hiredUserId, CV và điểm AI | skillsMissing JSON; interviewQuestions JSON; strengths/concerns JSON | Backend hiện thiếu các trường frontend/đặc tả cần |
| Application | rawCvText, matchScore và recommendation | screeningStatus; attempts; nextAttemptAt; claimedAt; runId; screeningVersion; lastErrorCode | Theo dõi tác vụ nền, retry/recovery và loại kết quả cũ |
| Application | jobId | jobSnapshot JSON; sourceHash; evaluatedRequirementsVersion; modelName; promptVersion; screenedAt | Biết điểm dựa trên JD/model nào, không nhầm điểm cũ với JD mới |
| Application | cvFileUrl | cvStorageKey; cvOriginalName; cvMimeType; cvSizeBytes; cvSha256 | Lưu file private; không tin đường dẫn do client gửi |
| Application | status, updatedAt | version int; rejectionReason nullable | Kiểm soát đổi trạng thái đồng thời và lý do HR |
| Interview | applicationId, interviewerId, round, scheduledAt, meetingLink, result, score, feedback | unique(applicationId,round); version; calendarStatus | Tránh vòng trùng, theo dõi tạo lịch thật |
| OnboardingTask | userId, category, title, dueDay, isCompleted | templateKey nullable và unique(userId,templateKey) nếu TV3 đồng ý | Chống sinh trùng 5 task; task tự tạo ngoài template vẫn được phép |
| User | unique email, role, departmentId, managerId, joinedDate | Cơ chế activation/reset do lead sở hữu | Không gửi passwordHash hoặc mật khẩu trong response |
| automation_events mới | Chưa tồn tại | eventId PK, type, aggregateId, payload JSON, status, attempts, nextAttemptAt, lease/runId, lastErrorCode, sentAt/completedAt | Outbox bền cho thư/lịch; không mất sự kiện khi server restart |

Chi tiết kiểu dữ liệu: id dương; score decimal 0..100 chuyển sang number ở response; ngày giờ JSON dạng ISO 8601; danh sách JSON mặc định `[]` ở serializer; nullable thể hiện rõ bằng `null`. Timestamp lease dùng UTC. Các giới hạn string bám chiều dài cột hiện có để tránh lỗi MySQL cắt dữ liệu.

`screeningStatus` đề xuất: `PENDING | PROCESSING | COMPLETED | FAILED | NEEDS_REVIEW`. `calendarStatus`: `PENDING | READY | FAILED`. Outbox `status`: `PENDING | PROCESSING | SENT | FAILED`; SENT chỉ khi nhận callback xác nhận công việc hoàn tất, không phải vừa gửi HTTP.

Nên giữ `cvFileUrl` trong bước tương thích nhưng trả URL download có xác thực, không dùng đường dẫn ổ đĩa. Di chuyển hồ sơ mẫu cần mapping/backfill; không giả định `/uploads/sample_cv.pdf` là file thật. Trường thiếu file được hiển thị “CV chưa có” và không đem đi chấm.

### 4.2 Index và migration

- Giữ unique `(jobId, candidateEmail)` đang có; chuẩn hóa trim + lowercase trước lưu; xử lý lỗi unique thành 409.
- Index jobs `(status, departmentId, createdAt, id)` và applications `(jobId, status, createdAt, id)` theo truy vấn thực tế; không thêm index trùng chỉ để đủ danh sách.
- Index hàng chờ screening `(screeningStatus, nextAttemptAt)`; outbox `(status, nextAttemptAt)`.
- Unique interviews `(applicationId, round)`; unique onboarding template và eventId ổn định cho dedupe.
- Backfill version=1; hồ sơ chưa có score đặt PENDING chỉ nếu có file hợp lệ; score mẫu không mặc định là AI thật.
- Viết migration up/down và kiểm tra database mới lẫn database có dữ liệu. Khi migration được dùng, thống nhất tắt `synchronize` ở môi trường dùng chung để tránh drift.
- Rollback cần giữ được hồ sơ; backup trước thay enum/xóa cột. Nếu dữ liệu DRAFT đã có, rollback enum cần mapping có chủ đích.

### 4.3 Dữ liệu dùng để AI đánh giá

- Snapshot lúc submit: title, description, requirements, department và requirementsVersion. Không đưa full User hoặc bí mật hệ thống vào prompt.
- Chỉ gửi phần CV/JD cần thiết; các trường liên hệ không là tiêu chí điểm số.
- Khi JD đổi, không lặng lẽ viết lại điểm cũ. UI ghi “đánh giá theo JD phiên bản N”; HR có thể bấm chấm lại theo phiên bản mới.
- `screeningVersion/runId` mới cho mỗi lần chấm lại. Kết quả worker chỉ được commit nếu vẫn khớp phiên bản và claim của lần chạy đó.

## 5. Hợp đồng API đề xuất

### 5.1 Quy ước chung

- Prefix `/api`; đường dẫn trong bảng đã bao gồm prefix.
- `PUBLIC` không cần JWT. HR/SUPERADMIN là operator tuyển dụng. Manager đọc theo phạm vi phòng ban; ghi kết quả chỉ khi được phân công. Employee không được xem CV hoặc hồ sơ tuyển dụng nội bộ.
- Không lấy `createdBy`, userId, role, matchScore, rawCvText, storage path hoặc hiredUserId từ payload công khai.
- DTO validate id dương, enum, độ dài và trường thừa; query page >=1, pageSize 1..100, mặc định 20; sort theo allowlist; ngày giờ có offset.
- Chỉ trả dữ liệu ứng viên cho route nội bộ có quyền. Response nộp đơn công khai chỉ gồm biên nhận tối thiểu.
- Response JSON giữ envelope đang có: `{success,statusCode,data,timestamp}`. `apiClient` đã unwrap `data`; domain API không unwrap lần nữa.
- Khi chuyển danh sách từ array sang `{items,page,pageSize,total}`, sửa đồng thời backend, types, API client và các consumer; ghi breaking change cho nhóm.
- File dùng stream/download riêng, không đi qua JSON wrapper; thống nhất với lead cách bypass interceptor cho route này.
- Lỗi dự kiến: 400 input; 401 token; 403 thiếu quyền; 404 không tồn tại/ngoài phạm vi; 409 trùng/xung đột trạng thái; 413 quá dung lượng; 415 không phải PDF; 422 PDF hỏng/không trích text; 429 hạn mức; 503 AI/integration chưa sẵn sàng. Thông báo không chứa raw SQL, đường dẫn nội bộ hoặc API key.

## 6. Quy tắc nghiệp vụ và luồng tích hợp

### 6.1 Tin tuyển dụng

- Tin mới mặc định DRAFT; OPEN yêu cầu title, department hợp lệ, description, requirements không rỗng sau trim.
- Public chỉ đọc OPEN; đóng tin không xóa hồ sơ cũ. Không hard-delete job có ứng viên vì quan hệ Application hiện CASCADE.
- CLOSED có thể mở lại theo D04. Sửa requirements tăng requirementsVersion; sửa lương/địa điểm không tự tăng phiên bản tiêu chí AI.
- Submit và đóng tin đồng thời cần thứ tự nhất quán: transaction kiểm tra/khóa job OPEN trước lưu Application; lệnh đóng dùng cùng hàng job. Không dựa vào trạng thái frontend.

### 6.2 Hồ sơ và trạng thái ATS

| Từ | Sang | Đường thực hiện | Điều kiện |
| --- | --- | --- | --- |
| APPLIED | INTERVIEWING | Tạo lịch phỏng vấn thành công trong DB | Interviewer hợp lệ, giờ tương lai, round hợp lệ |
| APPLIED | REJECTED | PATCH status | HR xác nhận, lưu lý do |
| INTERVIEWING | OFFERED | PATCH status | Vòng mới nhất PASSED theo D06 |
| INTERVIEWING | REJECTED | PATCH status | HR xác nhận, lưu lý do |
| OFFERED | HIRED | POST hire | Transaction tạo user/task thành công |
| OFFERED | REJECTED | PATCH status | HR xác nhận |
| HIRED | Không | Terminal | Muốn hủy phải là quy trình riêng, ngoài scope |
| REJECTED | Không ở bản 1.0 | Terminal | Mở lại là mở rộng, cần lý do và audit riêng |

Chấm AI độc lập với trạng thái ATS: AI recommendation=REJECT không tự chuyển ứng viên sang REJECTED. HR quyết định. Thao tác kéo sang INTERVIEWING mở modal lịch; kéo sang HIRED mở xác nhận hire; không gọi PATCH status để vượt side effect.

Mọi đổi trạng thái kiểm tra version. Request cũ trả 409 và UI tải lại hồ sơ; request lặp hire trả cùng hiredUserId nếu đã hoàn tất, không phát sinh bản ghi/thư lần nữa.

### 6.3 Upload và screening nền

1. Ứng viên chọn PDF; frontend kiểm tra kích thước/type để phản hồi sớm. Server kiểm tra lại phần mở rộng, MIME, chữ ký PDF, kích thước và khả năng parse.
2. Preview trả dữ liệu nullable để người dùng sửa; PDF scan chưa hỗ trợ OCR được báo rõ. AI preview lỗi vẫn cho nhập tay và nộp file hợp lệ.
3. Submit không tin thông tin AI/đường dẫn từ client. File được ghi private với tên ngẫu nhiên; transaction lưu hồ sơ, snapshot JD và trạng thái PENDING.
4. Response 201 trả ngay sau khi lưu bền; không chờ Gemini. Nếu DB thất bại, dọn file vừa ghi; job cleanup xử lý file mồ côi sau crash.
5. Worker claim PENDING bằng thao tác DB có điều kiện/lock. Cap concurrency mặc định 1, cấu hình được. Không coi EventEmitter trong RAM là hàng đợi bền.
6. Parse text có giới hạn thời gian/dung lượng; PDF không có text đặt NEEDS_REVIEW. Text quá giới hạn phải báo warning/chính sách rút gọn, không cắt âm thầm rồi tuyên bố đọc toàn bộ.
7. Gọi Gemini với schema/rubric version; validate JSON, score hữu hạn 0..100, enum, array và đủ 3 câu hỏi. Sai schema không ghi điểm giả.
8. Commit kết quả khi runId/version/lease còn hợp lệ. Ghi model/promptVersion/JD version và thời điểm.
9. Lỗi tạm thời thử tối đa 3 lần tổng cộng (1 lần đầu + 2 retry), backoff đề xuất 5s/15s có jitter và tôn trọng Retry-After. File sai/schema sai sau một lần sửa định dạng thì dừng và báo rõ; lời gọi sửa định dạng cũng phải nằm trong ngân sách tối đa 3 lần.
10. Sau restart, quét PENDING và PROCESSING hết lease; tác vụ cũ về trễ không được đè kết quả mới. Lease đề xuất 120s, timeout lời gọi AI 45s; gia hạn khi xử lý dài hoặc giảm giới hạn đầu vào.
11. Frontend poll 3–5s khi còn pending, ngừng lúc terminal/đổi job/unmount; có nút refresh và tải lại thủ công nếu thời gian chờ dài.

Rubric đề xuất để nhóm duyệt: kỹ năng bắt buộc 50%, kinh nghiệm liên quan 30%, bằng chứng dự án/chứng chỉ liên quan 20%. Điểm là gợi ý đánh giá theo JD, không là xác suất thành công. Không dùng tên, giới tính, tuổi, ảnh hoặc tình trạng gia đình để chấm. Chưa có bằng chứng phải diễn đạt “chưa thấy trong CV”. Không làm theo chỉ dẫn nằm trong CV; coi CV là dữ liệu, không phải system prompt.

Nhãn đề xuất: >=85 STRONG_HIRE; 70–84.99 HIRE; 50–69.99 CONSIDER; <50 REJECT. Backend có thể suy ra nhãn từ điểm để tránh score/label mâu thuẫn; chốt rubric và mapping trước P06. Lưu score chưa chấm là null, không hiển thị 0%.

### 6.4 Phỏng vấn, n8n và thư mời

- Lịch nhập theo Asia/Ho_Chi_Minh, gửi ISO có timezone, lưu UTC. Round dương, không trùng trong application; thời điểm phải ở tương lai.
- Transaction tạo Interview, cập nhật Application và ghi outbox cùng một lần. Sau commit dispatcher gọi workflow.
- Outbox có eventId ổn định; cùng event retry không tạo Google Calendar event/email mới. Workflow phải lưu nhận diện dedupe bền, không chỉ trong RAM.
- Riêng email có tình huống nhà cung cấp đã nhận nhưng workflow mất kết nối trước khi lưu xác nhận. Nếu provider không hỗ trợ idempotency, không hứa gửi đúng một lần tuyệt đối: giữ trạng thái kết quả chưa chắc chắn, đối soát provider trước khi retry; ghi giới hạn này trong evidence. Không retry mù khi chưa rõ thư đã gửi hay chưa.
- Payload chỉ gửi dữ liệu cần thiết: eventId, interviewId, applicationId, candidateName/email, interviewerName/email, scheduledAt, round, callback reference. Không gửi CV hoặc API key.
- Callback xác thực bằng cơ chế lead cung cấp, kiểm tra eventId và aggregateId. Callback lặp là no-op; callback cũ không đổi kết quả mới. Không nhận URL callback tùy ý từ payload công khai.
- UI tách “Đã lưu lịch” và “Đã gửi thư/Tạo Meet”. HTTP 2xx từ n8n chỉ xác nhận tiếp nhận, chưa chứng minh workflow hoàn tất.
- Nếu Google Meet chưa cấu hình, có thể dùng link họp HR nhập đã validate cho mốc demo nhỏ; không đánh dấu tiêu chí tự sinh Meet hoàn tất.
- Không vừa gửi SMTP trong backend vừa gửi qua n8n. Chọn một owner gửi thư theo D10.
- Email/Telegram demo chỉ tới hộp thư/tài khoản test do nhóm sở hữu; automation không chạy định kỳ thực tế trong giai đoạn viết kế hoạch.

### 6.5 Nhận việc một chạm và bàn giao onboarding

Transaction đề xuất:

1. Xác thực HR/SUPERADMIN; khóa hàng Application để chống double click/concurrent hire.
2. Nếu HIRED và hiredUserId còn hợp lệ, trả kết quả cũ. Nếu trạng thái không OFFERED hoặc kết quả PV không hợp lệ, trả 409.
3. Kiểm tra email đã có User, department/manager đang hợp lệ, joinedDate hợp lệ; trường hợp email tồn tại trả 409 theo D13, không tự sửa user cũ.
4. Tạo User role EMPLOYEE với hash mật khẩu ngẫu nhiên không công khai; dùng activation/reset của lead để cấp truy cập. Không hard-code password chung.
5. Tạo 5 OnboardingTask theo template được TV3 duyệt, hoặc gọi hàm TV3 có nhận cùng transaction manager. Hàm mở transaction riêng sẽ phá tính nguyên tử.
6. Cập nhật status=HIRED, hiredUserId và version; ghi outbox employee.hired. Commit tất cả cùng lúc.
7. Sau commit gửi thông báo/activation qua cơ chế thống nhất; gửi mail lỗi chỉ retry thông báo, không rollback nhân viên đã tạo.
8. Xuất dữ liệu kỹ năng thiếu cho TV4 theo lookup application/hiredUserId; không tự gán khóa học nếu chưa nhận scope đó.

Template onboarding **đề xuất v1**, TV3 là đầu mối chốt nội dung:

| templateKey | Title | Category | dueDay |
| --- | --- | --- | --- |
| paperwork-v1 | Nộp hồ sơ nhân sự theo hướng dẫn | PAPERWORK | 1 |
| equipment-v1 | Nhận máy và xác nhận thiết bị | EQUIPMENT | 1 |
| accounts-v1 | Hoàn thành thiết lập tài khoản làm việc | EQUIPMENT | 3 |
| mentor-v1 | Họp định hướng với quản lý hoặc mentor | MEETING | 7 |
| security-v1 | Hoàn thành hướng dẫn an toàn thông tin | TRAINING | 14 |

`dueDay` là số ngày tương đối so với joinedDate; quy ước ngày 1 = joinedDate. Đây là 5 mốc ban đầu trong hành trình 30 ngày, không phải cam kết đã có toàn bộ chương trình đào tạo 30 ngày. Cả 5 task ban đầu `isCompleted=false`, `completedAt=null`.

Mốc nghiệm thu:

- **M1 sau P04:** HR tạo/mở tin, ứng viên tìm và nộp CV, hồ sơ lưu thật, không cần AI để nộp được.

## 9. Ma trận kiểm thử và dữ liệu nghiệm thu

### 9.1 Cách kiểm thử

- Unit: DTO/schema, rubric mapping, state machine, normalization, serializer, retry policy; deterministic, không gọi Gemini thật.
- Integration: MySQL thật cho unique constraint, transaction, khóa/version, migration, scope query và outbox; Gemini/n8n stub để tạo lỗi xác định.
- Component: form/dropzone, loading/empty/error, stale responses, drawer, modal, rollback khi mutation lỗi.
- E2E: browser → API → DB cho critical path; live AI/n8n smoke tách riêng có credentials test và hạn mức.
- Fixture dữ liệu giả phải được nhận diện là giả. Tránh test chỉ mock toàn bộ repository rồi khẳng định concurrency/transaction đúng.

## 10. Vận hành, khắc phục lỗi và Definition of Done

### 10.1 Lệnh nền đã biết và điều kiện dùng

Chạy từ root repository cho Docker, từ đúng backend/frontend cho Node. Đây là hướng dẫn cho giai đoạn triển khai, không phải xác nhận các lệnh đã chạy trong bước lập kế hoạch.

```powershell
# Root repository; cần Docker Engine đã chạy
docker compose up -d mysql

# Trong backend: kiểm tra biên dịch không phụ thuộc npm .cmd shim
node ./node_modules/@nestjs/cli/bin/nest.js build

# Trong frontend
node ./node_modules/typescript/bin/tsc -b
node ./node_modules/vite/bin/vite.js build
```

Chạy dev có thể dùng `node ./node_modules/@nestjs/cli/bin/nest.js start --watch` trong backend và `node ./node_modules/vite/bin/vite.js --host 127.0.0.1` trong frontend. Kiểm tra máy hiện tại trước khi mở thêm server trùng cổng. Nếu bcrypt báo thiếu native binding sau install `--ignore-scripts`, xử lý cài/rebuild đúng dependency và quyền môi trường; build TS không phát hiện vấn đề native này.

Scripts test/migration/worker sẽ được bổ sung và ghi command chính xác ở P01/P02, chưa coi `npm test` hoặc `npm run migration:*` là có sẵn. Không ghi đè .env đang có hoặc xóa volume để tái lập nhanh.

### 10.4 Definition of Done chung

Một đầu việc chỉ được tích khi:

1. Luồng đã chạy theo scope của task và acceptance của phase; lưu dữ liệu thật nếu task yêu cầu DB.
2. Các case test liên quan đã đạt, có evidence và ghi rõ stub/live.
3. Quyền truy cập, input lỗi và tình huống thất bại quan trọng đã được kiểm tra.
4. UI có loading/empty/error/success đúng; không báo thành công khi chưa thành công.
5. Types/API/schema/tài liệu được cập nhật đồng bộ; không TODO quan trọng bị che bằng dữ liệu mẫu.
6. Không có secret, dữ liệu CV thật hoặc artifact build bị commit nhầm.
7. Task/phase phụ thuộc thành viên khác đã nhận bàn giao cần thiết; nếu chưa có, ghi BLOCKED rõ chứ không tích Done.
8. Commit/PR hoặc evidence được ghi vào PROGRESS.md. Ghi reviewer khi nhiệm vụ cần review chung.
